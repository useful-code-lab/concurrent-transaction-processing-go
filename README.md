# Concurrent Transaction Processing with Go, RabbitMQ & PostgreSQL

Практический пример того, как проектировать систему, которая **безопасно обрабатывает множество одновременных изменений одного ресурса**.

Проект показывает, как с помощью **Go, RabbitMQ, PostgreSQL и WebSocket** построить асинхронную архитектуру, в которой конкурентные запросы не приводят к потере обновлений и конфликтам состояния.

## Зачем смотреть этот проект?

Если вы разрабатываете backend-системы, где несколько пользователей или сервисов могут одновременно изменять одни и те же данные, этот проект поможет разобраться с реальной проблемой **concurrency**.

На практике вы сможете увидеть, как:

* принимать большое количество одновременных запросов;
* не блокировать API во время записи в базу;
* передавать операции через персистентную очередь RabbitMQ;
* последовательно обрабатывать конфликтующие изменения;
* использовать атомарные SQL-операции PostgreSQL;
* применять optimistic locking для контроля версий;
* предотвращать потерю обновлений при конкурентной записи;
* синхронизировать несколько клиентов через WebSocket;
* реализовать автоматический retry с exponential backoff;
* разделять независимые ресурсы на изолированные комнаты;
* запускать всю систему в Kubernetes через Minikube.

Главная ценность проекта — не отдельный API или CRUD-операции, а **готовый учебный пример архитектуры для конкурентной обработки изменений**.

---

## Какую проблему решает проект?

Представим ресурс с версией `10`.

Одновременно приходят два запроса:

```text
Client A → изменить ресурс → версия 10
Client B → изменить ресурс → версия 10
```

Если оба запроса напрямую работают с базой, возникает классическая проблема конкурентного доступа:

```text
A читает version = 10
B читает version = 10

A записывает изменение
B записывает изменение

→ одно из изменений может потеряться
```

Проект демонстрирует другой подход:

```text
Clients
   │
   │ WebSocket
   ▼
API Gateway
   │
   │ asynchronous command
   ▼
RabbitMQ
   │
   │ ordered processing
   ▼
Worker
   │
   │ atomic SQL + version check
   ▼
PostgreSQL
   │
   │ successful update
   ▼
WebSocket broadcast
   │
   ▼
Connected Clients
```

Запрос пользователя не обязан непосредственно менять состояние базы. Сначала команда попадает в персистентную очередь, после чего worker выполняет изменение в контролируемом порядке.

## Что можно изучить на этом проекте

### 1. Асинхронную обработку команд

API Gateway быстро принимает запрос и передаёт задачу в RabbitMQ вместо того, чтобы выполнять всю операцию синхронно.

Это позволяет отделить:

```text
приём запроса
```

от

```text
обработки и сохранения изменения
```

Такой подход полезен для систем с большим количеством событий, фоновых операций и переменной нагрузкой.

### 2. Конкурентный доступ к данным

Проект на практическом примере показывает, почему одновременная работа нескольких клиентов с одним состоянием может привести к конфликтам.

Версия ресурса используется для контроля актуальности операции.

Условно:

```text
Current version: 10

Client A → update version 10 → success → version 11
Client B → update version 10 → conflict
```

Клиент с устаревшей версией должен синхронизироваться с актуальным состоянием.

### 3. Optimistic Locking

Вместо глобальных mutex внутри приложения контроль конкурентных изменений выполняется на уровне состояния, хранящегося в PostgreSQL.

Это позволяет изучить практическое применение **optimistic concurrency control**.

### 4. RabbitMQ как слой упорядочивания

RabbitMQ выступает промежуточным persistent-слоем между API и worker.

Это позволяет:

* не терять команды при временных проблемах обработки;
* разгрузить API;
* отделить скорость приёма запросов от скорости обработки;
* централизовать последовательную обработку изменений.

### 5. WebSocket-синхронизацию

После успешного изменения состояния сервер уведомляет подключённых клиентов.

Клиенты получают актуальную версию:

```text
[SYNCHRONIZATION]
version: 8
```

После этого следующий запрос выполняется уже с актуальным состоянием.

Таким образом, проект демонстрирует не только запись данных, но и **распространение нового состояния обратно пользователям**.

# Архитектура

Проект состоит из трёх основных компонентов.

## API Gateway — `cmd/server`

Сервер отвечает за:

* WebSocket-соединения;
* идентификацию ресурса через `?id=...`;
* изоляцию клиентов по ресурсам;
* передачу команд в RabbitMQ;
* broadcast успешных изменений подключённым клиентам.

Пример подключения:

```text
ws://localhost:8080/ws?id=99
```

Каждый `id` представляет отдельный ресурс или комнату.

---

## Worker — `cmd/worker`

Worker получает команды из RabbitMQ и выполняет изменение в PostgreSQL.

Основная задача worker:

```text
RabbitMQ
    ↓
получение команды
    ↓
проверка версии
    ↓
атомарный SQL UPDATE / UPSERT
    ↓
новая версия
    ↓
уведомление API
```

Worker настроен на последовательную обработку сообщений:

```go
ch.Qos(1)
```

Это позволяет наглядно продемонстрировать модель, при которой конфликтующие операции проходят через контролируемую последовательность обработки.

---

## Client Simulator — `cmd/client`

Клиент используется для моделирования нескольких одновременно работающих пользователей.

Он:

* устанавливает WebSocket-соединение;
* отправляет изменения;
* получает broadcast от сервера;
* обновляет локальную версию ресурса;
* повторяет конфликтующие операции;
* использует exponential backoff.

По сути это небольшой генератор конкурентной нагрузки, позволяющий увидеть поведение системы в реальном времени.

---

# Что происходит при конкурентной нагрузке

После запуска несколько клиентов начинают изменять один и тот же ресурс.

Например:

```text
Client 1 ─┐
Client 2 ─┤
Client 3 ─┼──→ API → RabbitMQ → Worker → PostgreSQL
Client 4 ─┤
Client 5 ─┘
```

Worker последовательно обрабатывает команды:

```text
version 249
    ↓
version 250
    ↓
version 251
    ↓
version 252
    ↓
version 253
```

После успешного изменения клиенты получают актуальное состояние через WebSocket.

Это позволяет визуально наблюдать, как система обрабатывает конкурентные изменения вместо того, чтобы просто читать теорию о race conditions.

# Практический результат

После запуска проекта можно наблюдать в логах:

```text
[QUEUE] Processing resource ID 1
[DB] Updating version 249
[SUCCESS] Database updated to version 250
```

Клиенты получают:

```text
[SYNCHRONIZATION]
Current version: 250
```

И используют полученную версию для следующего изменения.

В результате можно увидеть полный цикл:

```text
Concurrent requests
       ↓
API
       ↓
RabbitMQ
       ↓
Worker
       ↓
Optimistic locking
       ↓
PostgreSQL
       ↓
WebSocket
       ↓
Client synchronization
```

# Технологии

* **Go** — backend и конкурентная обработка
* **RabbitMQ** — персистентная очередь сообщений
* **PostgreSQL** — хранение состояния и атомарные SQL-операции
* **WebSocket** — realtime-синхронизация клиентов
* **Docker** — контейнеризация сервисов
* **Kubernetes** — оркестрация компонентов
* **Minikube** — локальный Kubernetes-кластер

# Запуск проекта

## Требования

Перед запуском понадобятся:

* Go
* Docker
* Minikube
* kubectl
* WebSocket client, например `wscat`

---

## 1. Переключить Docker на Minikube

```bash
eval $(minikube docker-env)
```

---

## 2. Собрать Docker-образы

API:

```bash
docker build --target server -t concur-platform-server:v4 .
```

Worker:

```bash
docker build --target worker -t concur-platform-worker:v2 .
```

Client:

```bash
docker build --target client -t concur-platform-client:v2 .
```

---

## 3. Запустить Kubernetes-компоненты

```bash
kubectl apply -f k8s-platform.yaml
```

Проверить состояние:

```bash
kubectl get pods
```

После запуска все основные компоненты должны перейти в состояние:

```text
Running
```

# Проверка изоляции ресурсов

Можно самостоятельно подключиться к другому ресурсу.

Пробросить порт:

```bash
kubectl port-forward service/platform-server-service 8080:8080
```

Подключиться:

```bash
wscat -c "ws://localhost:8080/ws?id=99"
```

Ресурс `ID 99` будет иметь независимое состояние от фонового потока изменений ресурса `ID 1`.

Это позволяет проверить, что система умеет одновременно работать с несколькими независимыми ресурсами.

# Главная идея проекта

Главная идея — показать, как можно превратить поток хаотичных конкурентных запросов в контролируемый процесс:

```text
Много одновременных запросов
            ↓
       API Gateway
            ↓
      Persistent Queue
         RabbitMQ
            ↓
       Single Worker
            ↓
 Optimistic Concurrency Control
            ↓
        PostgreSQL
            ↓
     WebSocket Broadcast
            ↓
    Синхронизация клиентов
```

Вместо попытки решать всю конкуренцию с помощью mutex внутри приложения проект переносит критическую последовательность операций в **очередь сообщений + атомарные операции базы данных + контроль версий**.

Именно поэтому репозиторий представляет интерес как учебный и экспериментальный пример архитектуры систем, где несколько пользователей одновременно изменяют одни и те же данные.
